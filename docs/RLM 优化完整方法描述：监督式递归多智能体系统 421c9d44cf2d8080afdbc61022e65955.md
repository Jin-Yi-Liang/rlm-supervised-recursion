# RLM 优化完整方法描述：监督式递归多智能体系统

**文档类型**：软件设计说明书（Software Design Specification, SDS）
**文档版本**：V1.0
**设计基线**：[RLM 自研代码仓库](https://github.com/Jin-Yi-Liang/rlm-supervised-recursion/tree/learn/repl)
**设计范围**：Root Agent 全局任务规划与进度管理；Supervisor Agent 对 Sub-Agent 的提交审查、反馈及原地修复。文中的所有模块均按最终系统统一描述，不按开发进度区分。

## 1. 系统概览

### 1.1 目标

在 Recursive Language Models（RLM）通过 Python REPL 外部保存上下文、调用子代理解决局部问题的基础上，引入两项协作机制：

**（A）全局规划与进度管理**：Root Agent 根据用户目标建立可追踪的计划与进度记录，明确整体目标、待处理事项、已完成内容、未解决问题、验收条件和结果引用，并根据执行反馈动态调整下一步。**计划的内部表示、任务之间的组织关系和调度算法暂不预设为 DAG、固定任务表或其他特定形式。**

**（B）独立的 Supervisor 校验**：Sub-Agent 在私有 REPL 中产生候选答案，并以变量引用方式提交。Supervisor Agent 具有自己的 LLM 会话、工具调用循环和 REPL，按需读取子代理提交快照及中间证据，决定接受、要求原地修复、判定规划存在问题，或认定本次审核无法完成。通过审核的结果才能进入全局已接受结果集。

**结果外置**是贯穿系统的数据传递约束：大块原始数据、中间变量、候选答案和最终子结果保存在外部受管理存储中。Agent 的模型上下文默认仅携带任务契约、状态摘要、结果句柄和按需读取的局部证据，不一次性展开全部数据。

### 1.2 范围边界

本规范定义 Root 的计划生成/修订、子任务派发、Child 的变量化提交、Supervisor 的独立 REPL 与跨 REPL 只读核查、原地继续、验收门控和最终汇总。模型调用、REPL 执行、日志与超时处理作为这些流程的必要支撑予以规定。独立的实时风险监控 Agent、长期经验记忆、自学习、外部知识检索索引优化、多模型路由均不属于本规范。

### 1.3 总体逻辑架构

```python
User / External Context
          |
          v
   Root Agent  <----------------------+
   (LLM + REPL + Agent Loop)          |
          |                           |
   register_plan/revise_plan          | task_state/result_receipt
          v                           |
   PlanManager / TaskLedger ----------+
          |
   dispatch_registered(task_id)
          v
   SubAgentDispatcher
          |
          v
   Child Agent (LLM + private REPL + Agent Loop)
          |
   submit_candidate(result_var, evidence_vars)
          v
   SubmissionRegistry -- immutable CandidateRef
          |
          v
   Supervisor Agent (LLM + own REPL + Agent Loop)
          |
          +--> StateBroker: list/inspect child vars, trace, input
          |                    |
          |                    v
          |             frozen Child submission view
          |
   submit_review(decision, evidence_refs, feedback)
          |
          v
   ReviewGate / TaskLedger
          |
          +--> ACCEPT ----> atomic commit ----> Root result receipt
          |
          +--> REVISE ----> same Child REPL/messages continue
          |
          +--> PLAN_ISSUE -> Root revises plan
          |
          +--> REVIEW_INCOMPLETE / FAIL -> no commit
```

**控制权划分**：Root 负责计划与任务决策；Child 负责具体执行；Supervisor 负责审查；Harness 负责真实进度记录、状态一致性、预算、版本、隔离及审核门控。调度约束由后续选定的规划方法决定，当前不预设任务依赖图。Supervisor 不得私自修改 Root 的计划或 Child 的执行变量；Child 不得自行将结果标记为全局已完成。

### 1.5 核心业务对象与不变量

- **Run**：一个用户全局任务的执行实例，拥有 `run_id`。
- **Task**：全局计划中的一个逻辑子任务，拥有稳定的 `task_id` 和对应验收条件。
- **ChildSession**：执行一个逻辑任务的代理会话，拥有持久 REPL、消息与历史。被拒后继续复用，不自动重建。
- **Candidate**：Child 对同一 Task 的第 `candidate_version` 次提交；它不是已接受结果。
- **Review**：Supervisor 针对某一 Candidate 的版本绑定审查意见。
- **Receipt**：只有通过审核并完成原子提交后才存在的可信结果句柄。

系统必须始终满足：①任务标识稳定可追踪；②计划修改可追溯；③Root 可查询当前整体目标、已完成事项、未完成事项和下一步可选行动；④审核绑定准确任务及候选版本；⑤候选快照审核期间不可变；⑥未审核通过不得写入全局 accepted_results；⑦相同提交不得重复生效；⑧ REVISE 保留 Child 原 REPL、messages、history；⑨最终返回前检查用户目标覆盖程度及必要结果是否完成。任务顺序、依赖规则与计划表示不作为当前固定不变量。

## 2. 从输入到运行结束的完整流程

### 2.1 创建执行会话

1. `SessionRuntime.start_run(user_request, context)` 分配 `run_id`，把用户任务原文存为 `GlobalTaskSpec`，把大体量原始上下文放入 Root REPL 或外部对象存储，生成 `context_ref`。
2. 初始化 Root LLM 客户端、Root REPL、消息历史及 TaskLedger；传给 Root 的初始 prompt 包含任务目标、可用规划/查询工具说明以及数据访问句柄，不自动展开全部大文本。
3. 创建空计划、空 accepted_results 集合和本次运行的 token/步骤/子调用预算。

### 2.2 Root 建立全局计划

1. Root 根据用户要求，必要时先在自己的 REPL 中探索输入的结构与范围。
2. Root 通过 create_plan、add_task、set_task_acceptance 等受控函数逐步建立计划草稿；Harness 内部构造固定类型的 PlanSpec 和 TaskSpec，而不要求模型手写完整 JSON。调用 commit_plan 后才进行整体校验及正式登记。
3. PlanManager 对已选择的计划表示进行确定性数据校验，包括字段类型、任务标识、输入引用、记录一致性及必要验收标准；不强制要求无环图或固定依赖结构。失败时返回结构化错误，不覆盖有效计划。
4. 验证通过后得到计划版本及可追踪进度状态。Root 通过 get_plan_state() 查看已完成事项、待处理事项、有效结果及问题，再自主决定下一步；不要求“解锁任务”这一固定调度模型。

### 2.3 任务派发与 Child 执行

1. Root 调用 REPL 提供的 `rlm_query(task_id)` 或 `rlm_query_batched(task_ids)`。有全局计划时，必须按已登记 `task_id` 派发，而不任意创建缺乏计划关联的新任务。
2. Dispatcher 查询权威进度状态，确认任务属于当前 Run、尚未完成、没有重复执行冲突且预算允许；如某种规划方法额外定义了任务执行条件，再由相应策略判断。首版不要求任务必须采用依赖图或前驱全部 ACCEPTED 才可执行。
3. Child 拥有独立的消息列表、REPL 与执行历史。Child 的初始模型上下文包含该 Task 的 instruction、criteria、适用的全局目标摘要及 `input_ref`；真实数据通过自己的 REPL 按需读取。
4. Child 可多轮调用 `execute_python` 处理输入、创建中间变量。所有变量默认只在 Child REPL 可见。
5. Child 完成后以代码调用 `submit_candidate(result_var, evidence_vars, summary)`，提供变量名而非答案全文。Harness 校验变量存在、表示可用、执行单元成功并冻结一个候选版本。
6. Child 暂停进入 `REVIEWING`。此时不允许其同时修改待审核数据。

### 2.4 Supervisor 独立审核与反馈

1. Dispatcher 创建 SupervisorSession。它拥有**独立的模型消息历史、独立 Python REPL、独立 Agent Loop**，不继承 Child 完整消息历史。
2. Supervisor 初始上下文只包含：全局任务和完成目标、该子任务契约、候选提交清单、候选版本号、可用证据目录和自身工具说明。
3. Supervisor 主动调用 `list_child_variables`、`inspect_child_variable`、`get_child_trace`、`read_candidate`、`get_global_task` 等只读接口，选择所需的变量及运行证据。必要时在**Supervisor 自身的 REPL**中复验逻辑、运算及数据覆盖性。
4. Supervisor 调用 `submit_review(...)` 提交结构化裁决。ReviewGate 严格验证 task_id/version/证据引用/决策枚举；格式不合法不得默认通过。
5. `ACCEPT`：ResultStore 将冻结候选转为不可变已接受结果，TaskLedger 原子更新任务完成状态，生成 Receipt 通知 Root。
6. `REVISE`：Harness 把 finding 与 requested_action 注入**同一个** ChildSession，状态转回 `RUNNING`；Child 在原 REPL 和原 messages 上补充操作，再提交下一版候选。
7. PLAN_ISSUE：若子任务目标不合理、数据范围错误、验收条件不合适或计划内容无法覆盖用户目标，停止本轮提交，通知 Root 调整整体计划；Supervisor 不直接修改计划。
8. `REVIEW_INCOMPLETE`：缺少有效证据、审核输出不合法或审核预算耗尽时，保持未接受状态；Root 可获取失败原因，选择修订或终止。

### 2.5 Root 更新进度、修订计划与最终回答

1. Root 调用 get_plan_state() 和 list_accepted_results() 获取全局目标、已完成事项、待处理事项、异常反馈及已接受结果引用，不重新加载所有 Child 的执行轨迹。
2. 若出现任务缺失、计划进度停滞、目标覆盖不足或 Supervisor 返回 PLAN_ISSUE，Root 使用 begin_plan_revision(expected_version) 创建修订草稿，经受控接口修改并由 commit_plan(draft_id) 校验提交。修订的目标是改善整体任务推进，不预设任务关系结构。
3. 对已解锁任务继续分发，直至所有必需任务 `ACCEPTED`，或因预算/不可恢复错误进入终止路径。
4. 最终提交之前调用 `validate_plan_completion(run_id)`；仅当全局必要任务完成、验收覆盖满足、无未决审核且结果引用一致时，允许 `finalize_run(final_answer_ref | final_text)` 标记成功。
5. 返回用户结果；若条件不满足，返回结构化的不完整/失败原因，不能把最后一轮部分内容伪装为成功。无论成功、失败或取消，SessionRuntime 都应结束计时并汇总 RunMetricsSnapshot，记录整次运行耗时、Root/Child/Supervisor 的调用与 Token、Tool Call 统计、候选提交、审核驳回与实际修复次数；保存计划版本、结果 Receipt 与三类 Agent 历史供实验追踪。

### 2.6 关键交互示例：使用受控函数创建计划

**设计决策**：Root LLM 不直接生成整个嵌套 JSON 或 dict，也不直接实例化内部计划类，而是调用固定的计划构建函数。Harness 内部通过类型化类保存计划，并在正式提交时统一验证。

```python
# Root REPL：创建计划草稿
draft_id = create_plan(goal="分别分析两组记录并给出总体比较")

add_task(
    draft_id,
    task_id="t-a",
    instruction="分析 A",
    input_ref="ctx:A",
    scope="覆盖 A 全部记录",
    required=True
)
set_task_acceptance(
    draft_id,
    task_id="t-a",
    checks=["覆盖 A 全部记录", "输出有效统计"],
    output_type="object"
)

add_task(
    draft_id,
    task_id="t-b",
    instruction="分析 B",
    input_ref="ctx:B",
    scope="覆盖 B 全部记录",
    required=True
)
set_task_acceptance(
    draft_id,
    task_id="t-b",
    checks=["覆盖 B 全部记录", "输出有效统计"],
    output_type="object"
)

plan_receipt = commit_plan(draft_id)
receipts = rlm_query_batched(["t-a", "t-b"])
print(get_plan_state())
print(receipts)

# Child REPL：通过变量引用提交
analysis = {"count": 100, "matched": 96, "ratio": 0.96}
source_rows = 100
submit_candidate(
    result_var="analysis",
    evidence_vars=["source_rows"],
    summary="已计算覆盖率，申请审核"
)

# Supervisor REPL：只读访问候选快照
catalog = list_child_variables()
candidate = read_candidate()
result = inspect_child_variable(name="analysis")
trace = get_child_trace(start=0, limit=10)
checked = result["value"]["matched"] / result["value"]["count"]
submit_review(
    task_id="t-a",
    candidate_version=1,
    decision="ACCEPT",
    finding="核对计算关系且覆盖范围满足任务契约",
    evidence_refs=[result["evidence_ref"]],
    requested_action=""
)
```

以上是目标接口的使用约定。create_plan 返回草稿 ID；add_task、set_task_acceptance 由 Harness 在草稿中创建和修改类型化任务对象；commit_plan 完成整体验证并登记计划。Supervisor 工具由当前审核作用域绑定候选任务与版本。## 3. 数据模型与接口数据合同

本节定义数据对象、字段类型、约束与交换合同。**统一设计决策：凡字段与结构可以固定的业务对象，一律由 Harness 定义 Python 类，并通过类方法或受控函数操作。**Root、Child、Supervisor 不负责手写完整 JSON 或嵌套 dict。JSON 仅用于外部 API、日志、存储和跨进程等必须进行序列化的边界；这些转换由 Harness 自动负责并校验。任意任务输入和 REPL 的动态计算数据不强制预设通用业务类，仍通过受控 ArtifactRef 按需访问。

### 3.1 GlobalTaskSpec：权威全局任务

GlobalTaskSpec 是由 Harness 在 Run 启动时创建的**类型化、只读业务对象**。Root 与 Supervisor 不生成完整 JSON，也不能直接修改用户目标。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class FinalAcceptanceSpec:
    required_task_policy: str
    checks: tuple[str, ...]

@dataclass(frozen=True)
class GlobalTaskSpec:
    run_id: str
    objective: str
    user_request_ref: str
    context_refs: tuple[str, ...]
    constraints: tuple[str, ...]
    final_acceptance: FinalAcceptanceSpec
```

Harness 创建全局任务的接口：`SessionRuntime.start_run(user_request: str, context: object, config: RunConfig) -> RunHandle`。内部由构造函数或工厂生成 GlobalTaskSpec，保存完整用户请求与大数据的独立引用。Root 或 Supervisor 通过 `get_global_task(include_full=False) -> GlobalTaskSpec` 获取目标约束；需要原始数据时调用受控读取函数。

`objective` 是全局目标的简短表述；`user_request_ref` 与 `context_refs` 是外部数据句柄；`constraints` 与 `final_acceptance` 提供整体完成判断依据。固定类结构不要求模型一次生成对应的 JSON 文本。只有存储或跨进程传输时才由 Harness 序列化这些值。

### 3.2 PlanSpec / TaskSpec：类型化类与函数构建契约

**设计决策**：固定格式的 PlanSpec、TaskSpec、AcceptanceSpec、OutputSpec 由 Harness 定义成 Python 类。Root Agent 不手写嵌套 JSON/dict，不直接修改权威类实例；仅调用 create_plan、add_task、set_task_acceptance、commit_plan 等受控函数。JSON 可作为持久化及跨进程交换格式，由 Harness 负责序列化、反序列化和验证。

**内部数据类型定义：**

```python
from dataclasses import dataclass, field

@dataclass(frozen=True)
class AcceptanceSpec:
    checks: tuple[str, ...]
    expected_count: int | None = None

@dataclass(frozen=True)
class OutputSpec:
    type_name: str
    required_fields: tuple[str, ...] = ()

# 草稿支持逐步填写（仅 Harness 持有）
@dataclass
class TaskDraft:
    task_id: str
    instruction: str
    scope: str
    input_refs: tuple[str, ...]
    required: bool = True
    acceptance: AcceptanceSpec | None = None
    output_schema: OutputSpec | None = None

@dataclass
class PlanDraft:
    draft_id: str
    run_id: str
    goal: str
    expected_version: int | None = None
    tasks: dict[str, TaskDraft] = field(default_factory=dict)

# 正式对象在 commit_plan 完整校验后构造
@dataclass(frozen=True)
class TaskSpec:
    task_id: str
    instruction: str
    scope: str
    input_refs: tuple[str, ...]
    acceptance: AcceptanceSpec
    output_schema: OutputSpec
    required: bool = True
    task_version: int = 1

@dataclass(frozen=True)
class PlanSpec:
    run_id: str
    plan_version: int
    goal: str
    tasks: tuple[TaskSpec, ...]
```

**暴露给 Root REPL 的固定接口声明：**

```python
def create_plan(goal: str) -> str: ...
def add_task(
    draft_id: str,
    task_id: str,
    instruction: str,
    input_ref: str,
    scope: str,
    required: bool = True
) -> None: ...
def set_task_acceptance(
    draft_id: str,
    task_id: str,
    checks: list[str],
    output_type: str = "object",
    required_fields: list[str] | None = None,
    expected_count: int | None = None
) -> None: ...
def commit_plan(draft_id: str) -> PlanReceipt: ...
def copy_plan(draft_id: str, goal: str | None = None) -> str: ...
def begin_plan_revision(expected_version: int) -> str: ...
def update_task(
    draft_id: str,
    task_id: str,
    instruction: str | None = None,
    input_ref: str | None = None,
    scope: str | None = None,
    required: bool | None = None
) -> None: ...
def remove_task(draft_id: str, task_id: str) -> None: ...
def discard_plan_draft(draft_id: str) -> None: ...
```

以上省略号仅出现在**接口声明**内，表示具体实现由 Harness 提供，绝不是要求模型在其代码中输出省略号。

- create_plan：创建 PlanDraft，返回草稿标识符；TaskDraft 可逐步填写 acceptance/output_schema，commit_plan 完整校验后构造 TaskSpec。PlanSpec/TaskSpec 只是目前表达目标与任务信息的类型化接口，不决定计划的调度或组织算法。
- add_task：检查 task_id、instruction、input_ref 等基础参数，增加任务草稿；默认验收条件尚未定义。
- set_task_acceptance：按固定参数补全验收条款和结果类型；不允许遗漏必需验收条件。
- commit_plan：将草稿转换为 PlanSpec/TaskSpec，检查数据合法性、任务标识、输入范围、必要验收等，再登记并返回 PlanReceipt；**不要求 DAG 或固定调度算法**。
- copy_plan：深度复制草稿数据并生成独立草稿标识，用于安全修改草案；不共享可变引用，不改动正式计划。
- begin_plan_revision：读取权威计划的指定版本形成新草稿；修改草稿后通过 commit_plan 提交，并校验乐观锁。

**类型约束与责任**：字段通过 dataclass 类型注解表达，但注解本身不会自动拒绝运行时错误值，所有输入必须由 Harness 校验。frozen=True 只限制实例属性重新赋值，并不能冻结任意嵌套可变对象；本例用 tuple 和不可变值对象保障内部结构。模型生成函数调用仍可能语法错误或参数不合法，因此应校验签名、值域和权限并向 Root 返回清晰的错误，而不是假设函数机制能消除所有格式问题。

**字段语义**：task_id 在 Run 内稳定唯一；instruction 为任务要求；scope 限定输入范围；input_refs 指向所需数据；required 指示是否属于必要目标；acceptance 为验收依据；output_schema 限定结果结构。任务间关系、优先级、顺序或计划表达方式属于后续规划方案，可作为扩展元数据，不纳入当前必需字段。Root 的计划应始终服务原始用户目标。

**其他固定格式对象的同一规则**：GlobalTaskSpec、TaskRecord、CandidateManifest、ReviewVerdict、ResultReceipt 也应定义类型化类；Child 和 Supervisor 通过 submit_candidate、submit_review 等固定函数提交简单参数，由 Harness 生成完整对象，不能要求模型自行填写版本号、哈希、凭证 ID 或整份 JSON。

### 3.3 TaskRecord：真实执行进度

任务状态由 TaskLedger 持有与更新。Root、Child、Supervisor 可以**查询 TaskRecord 的只读副本**，不能通过自己修改字典把某项任务伪装为已完成。

```python
from dataclasses import dataclass
from enum import StrEnum

class TaskStatus(StrEnum):
    PLANNED = "PLANNED"
    RUNNING = "RUNNING"
    SUBMITTED = "SUBMITTED"
    REVIEWING = "REVIEWING"
    REPAIRING = "REPAIRING"
    ACCEPTED = "ACCEPTED"
    PLAN_ISSUE = "PLAN_ISSUE"
    REVIEW_INCOMPLETE = "REVIEW_INCOMPLETE"
    FAILED = "FAILED"
    CANCELLED = "CANCELLED"

@dataclass(frozen=True)
class TaskRecord:
    run_id: str
    task_id: str
    plan_version: int
    task_version: int
    status: TaskStatus
    attempt_count: int = 0
    candidate_version: int = 0
    latest_review_id: str | None = None
    accepted_receipt_id: str | None = None
    last_error: str | None = None
    required: bool = True

    def is_accepted(self) -> bool:
        return self.status is TaskStatus.ACCEPTED
```

**操作接口**：

- `TaskLedger.get_task(run_id: str, task_id: str) -> TaskRecord`：返回任务状态的独立值对象。
- `TaskLedger.get_plan_state(run_id: str) -> PlanState`：返回本次任务的整体进度。
- `TaskLedger.transition_task(run_id: str, task_id: str, expected_status: TaskStatus, new_status: TaskStatus, event_id: str) -> TaskRecord`：由 Harness 验证合法状态转换和重复事件，再产生更新后的 TaskRecord；不向 LLM 暴露直接设置 `status` 的入口。
- `ReviewGate.commit_accepted_candidate(...)->ResultReceipt`：是任务正式进入 ACCEPTED 的唯一业务入口。

`attempt_count` 是执行尝试次数；`candidate_version` 是同一任务的结果提交版本；`latest_review_id`、`accepted_receipt_id` 是审核记录和已接受结果的引用。字段本身只是状态数据，不决定计划使用图、列表或其他组织方法。

**使用示例**：

```python
task = get_task("t-a")
print(task.status)
print(task.candidate_version)
print([task.is](http://task.is)_accepted())
```

这段代码只读取数据；不存在模型手写 TaskRecord JSON 的步骤。

### 3.4 ArtifactRef：变量与大对象引用（固定类）

ArtifactRef 是由 ArtifactStore/SubmissionRegistry 生成的**不可变引用值对象**，不暴露 Python 原始对象地址，也不要求 Child/Root/Supervisor 自行拼接引用 ID。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class ArtifactRef:
    ref_id: str
    run_id: str
    task_id: str
    candidate_version: int
    source_namespace: str
    variable_name: str
    value_type: str
    size_bytes: int
    content_hash: str
    encoding: str
    snapshot_id: str
```

**受控接口**：

- `ArtifactStore.freeze_variable(session: ChildSession, variable_name: str, snapshot_id: str) -> ArtifactRef`：Harness 检查变量并根据支持的类型冻结数据，生成哈希、版本与唯一引用。
- `ArtifactStore.get_artifact(ref: ArtifactRef, offset: int = 0, limit: int = 1000, path: str | None = None) -> ArtifactView`：获取部分或全部数据的受限副本，不返回可修改原 Child REPL 的对象。
- `StateBroker.inspect_child_variable(scope: ReviewScope, name: str, ...) -> ArtifactView`：Supervisor 的按需变量读取入口。

对象冻结对大文件可以采用内容寻址存储或不可变拷贝，对 JSON 兼容值可采用受控序列化；不能安全冻结的 Python 对象要返回 UNSUPPORTED_ARTIFACT。**`encoding="json"` 只说明存储编码，不表示模型需要输出 JSON。** `deepcopy` 不能作为所有对象的可靠冻结方案。

### 3.5 CandidateManifest：Sub-Agent 的提交协议

Child 只通过**函数参数**给出结果变量名、证据变量名和简短说明；Harness 负责创建完整的 CandidateManifest、SubmissionAck、版本号和引用，不要求 LLM 手写 JSON。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class SubmissionAck:
    status: str
    submission_id: str
    candidate_version: int

@dataclass(frozen=True)
class CandidateManifest:
    submission_id: str
    run_id: str
    task_id: str
    task_version: int
    candidate_version: int
    result_ref: ArtifactRef
    evidence_refs: tuple[ArtifactRef, ...]
    snapshot_id: str
    summary: str
    status: str
    idempotency_key: str
```

**Child REPL 对外接口**：

```python
def submit_candidate(
    result_var: str,
    evidence_vars: list[str] | None = None,
    summary: str = ""
) -> SubmissionAck: ...
```

**操作示例**：

```python
ack = submit_candidate(
    result_var="analysis",
    evidence_vars=["source_rows", "parsed_rows"],
    summary="结果已生成并请求审核"
)
print(ack.status)
print(ack.candidate_version)
```

内部调用 `SubmissionRegistry.prepare_submission(...)` 暂存提交意图；仅在当前 `execute_python` 代码单元成功结束后，才调用 `SubmissionRegistry.finalize_submission(...)->CandidateManifest` 冻结结果并产生有效提交。执行失败则 `abort_submission(...)`，不得进入 REVIEWING。

`submission_id`、`candidate_version`、`result_ref`、`snapshot_id`、哈希及 `idempotency_key` 均由 Harness 分配，Child 不得自行填写。一次代码执行单元最多接受一个有效提交；候选的数据值不进入 Child 的最终模型文本，而是通过 `result_ref` 供 Supervisor 按需读取。提交成功只是 SUBMITTED，**不是 ACCEPTED**。

### 3.6 ReviewVerdict：Supervisor 审核结果

Supervisor 不需要输出一份 JSON Verdict，也不能指定 `review_id`、`review_status`。它通过具有固定参数签名的 `submit_review()` 调用 Harness；ReviewGate 检查字段、作用域、候选版本与证据权限之后，才生成 ReviewVerdict 对象。

```python
from dataclasses import dataclass
from enum import StrEnum

class ReviewDecision(StrEnum):
    ACCEPT = "ACCEPT"
    REVISE = "REVISE"
    PLAN_ISSUE = "PLAN_ISSUE"
    REVIEW_INCOMPLETE = "REVIEW_INCOMPLETE"

@dataclass(frozen=True)
class ReviewVerdict:
    review_id: str
    run_id: str
    task_id: str
    candidate_version: int
    decision: ReviewDecision
    finding: str
    evidence_refs: tuple[str, ...]
    requested_action: str
    review_status: str

@dataclass(frozen=True)
class ReviewSubmissionAck:
    accepted_by_gate: bool
    review_id: str | None
    error_message: str | None = None
```

**Supervisor REPL 的固定函数**：

```python
def submit_review(
    task_id: str,
    candidate_version: int,
    decision: str,
    finding: str,
    evidence_refs: list[str],
    requested_action: str = ""
) -> ReviewSubmissionAck: ...
```

**使用示例**：

```python
ack = submit_review(
    task_id="t-a",
    candidate_version=2,
    decision="REVISE",
    finding="缺少一部分记录",
    evidence_refs=[source_ref],
    requested_action="重新核对覆盖范围并补全缺失记录"
)
print(ack.accepted_by_gate)
```

审核决定分别表示：ACCEPT 为有证据支持通过；REVISE 为可修复局部错误；PLAN_ISSUE 为计划目标、范围或输入合同存在问题；REVIEW_INCOMPLETE 为证据或审核能力不足。REVISE 必须指定非空修复动作，ACCEPT 必须引用匹配候选版本的有效证据。ReviewGate 统一校验。**调用了 submit_review 不等于已正式接受候选结果**；只有合法的 ACCEPT 经过 ResultStore 提交才会生成 ResultReceipt。

### 3.7 ResultReceipt：已接受子任务的结果凭证

ResultReceipt 由 ReviewGate / ResultStore 在候选通过审核并正式提交后创建。Root 通过类属性和只读查询函数使用它，不得手写 Receipt JSON 或直接构造带 ACCEPTED 的任务凭证。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class ResultReceipt:
    receipt_id: str
    run_id: str
    task_id: str
    candidate_version: int
    review_id: str
    result_ref: ArtifactRef
    status: str = "ACCEPTED"

    def is_accepted(self) -> bool:
        return self.status == "ACCEPTED"
```

**受控接口**：

- `ReviewGate.commit_accepted_candidate(run_id: str, task_id: str, candidate_version: int, review_id: str, expected_task_version: int) -> ResultReceipt`：校验审核结果并进行幂等提交。
- `ResultStore.get_receipt(run_id: str, task_id: str) -> ResultReceipt | None`：查询已接受结果凭证。
- `[ResultStore.read](http://ResultStore.read)_accepted_result(receipt_id: str, path: str | None = None, offset: int = 0, limit: int = 1000) -> ArtifactView`：按需读取大对象内容。

**Root REPL 用法**：

```python
receipt = rlm_query("t-a")
print(receipt.task_id)
print([receipt.is](http://receipt.is)_accepted())
result = read_accepted_result(receipt.receipt_id, path="\$.ratio")
```

Root 默认接收一个轻量 ResultReceipt 或其 ID，而不是 Child 的全部计算结果、执行轨迹和变量。对于需要把对象传给其他模型/进程的场合，Harness 可调用受控序列化器进行转换，模型不负责构造 JSON。

除前述主要对象，模块接口里反复出现的其他固定格式返回值也应在 `schemas.py` 中定义类型化类，避免一部分使用 dataclass、另一部分仍让模型手动生成任意 dict。

### 3.9 运行统计数据模型（固定类，禁止模型手写统计 JSON）

运行统计是 Root 全局进度与 Supervisor 验收闭环的基础**观测接口**，不是第三个独立 Agent 或研究方向。每条记录由 Harness 在实际事件发生时采集，再生成类型化的统计快照；Root/Child/Supervisor 无权直接设置统计计数器。指标须能按 `run_id`、`task_id`、`agent_role`（ROOT/CHILD/SUPERVISOR）、`candidate_version`、`review_id` 关联。

**底层事件类与聚合结果：**

```python
from dataclasses import dataclass
```

**主要统计指标的统一口径：**

| 指标 | 定义与分母 | 来源 |
| --- | --- | --- |
| 整次 Run 总耗时 | 从 `start_run` 正式开始到完成/失败/取消的墙钟历时，使用单调时钟；即使任务失败也记录 | SessionRuntime |
| Root / Child / Supervisor 耗时 | 由各自执行阶段的开始结束事件记录，可有嵌套或并发；这些数值**不能简单相加当作 Run 总耗时** | 通用 Agent Loop / Dispatcher / Supervisor |
| LLM 请求数、失败数、耗时 | 一次 API 请求计一次；重试单独计次；完成/超时/报错均记事件 | `call_llm` |
| 输入 / 输出 Token | 优先使用模型 API 原生 usage；不可用则标注估算来源；coverage 为有可信 usage 的模型请求比例 | LLM Client |
| Tool Call 次数 | 每个模型尝试发出的工具调用各计一次，格式异常调用也计入 | `call_llm` / ToolRegistry |
| Tool Call 协议合规率 | `protocol_valid / tool_calls`；检查 id、function、arguments 结构与完整性；无调用时为 N/A | ToolRegistry |
| Tool 参数有效率 | `arguments_valid / tool_calls`；检查工具是否存在及参数能否通过 schema/类型/权限的静态校验；与实际执行成功分开统计 | ToolRegistry / `do_repl` |
| Tool 执行成功率 | `tool_execution_success / executed_tool_calls`；以结构化 `ExecutionResult.success` 判断，不能依据 stdout 看起来正常判断 | REPLRuntime |
| Tool Call **语义准确率** | `tool_semantic_correct / tool_semantic_evaluated`；需独立真值、可执行断言或人工标注；没有独立核验时返回 **N/A**，不得把执行成功率命名为准确率 | 离线 Evaluator |
| Child 有效提交次数 | CandidateManifest 成功冻结后计数；失败的提交意图另计，不算有效提交 | SubmissionRegistry |
| Supervisor 驳回次数 | 有效候选收到 `REVISE` 时计一次；同一 review_id 重复提交不能重复计数；`PLAN_ISSUE` / `REVIEW_INCOMPLETE` **单列** | ReviewGate |
| 驳回率 | `REVISE 次数 / (REVISE 次数 + ACCEPT 次数)`；仅在有有效审核裁决且分母大于 0 时有值，不把审核未完成混入 | MetricsCollector |
| 修复尝试次数 | Child 收到 REVISE 后真正继续执行的次数；同一任务多次 REVISE 可累积 | Dispatcher |
| 修复后接受的任务数 | 至少被 REVISE 一次、随后在相同逻辑任务上获得 ACCEPT 的去重 task_id 数量 | ReviewGate / TaskLedger |
| 修复成功率 | 已结束且至少经历一次 REVISE 的任务中，最终获得 ACCEPT 的任务数 / 这些已结束任务的数量；仍在运行的任务单列 | MetricsCollector |
| 完成任务数/总任务数 | 按 TaskLedger 中唯一 task_id 的有效状态统计；任务计划增删与版本需要明确对应时点，避免重复计数 | TaskLedger |
| 审核额外成本 | Supervisor 的 LLM 调用、Token、时长，以及由 REVISE 触发的 Child 额外调用；相对于无审核基线比较 | MetricsCollector |

**“Tool Call 准确率”必须拆开**：工具调用协议合法、调用参数合法、Python 代码执行不报错、实际达成子任务目标是四个不同概念。后者如果没有可验证的目标结果，则无法从一次运行日志自动精确计算。Supervisor 是否 ACCEPT 也不能被直接当作独立真值标签。

**耗时与并发约定**：单次运行总耗时用 `time.perf_counter_ns()` 的结束值减开始值。单个请求/工具的时长同样使用单调时钟。对并发 Sub-Agent，可分别报告工作时长求和和墙钟时长，但不能把并发时间叠加后的总和解释为实际用户等待时长。事件另外记录 UTC 时间戳用于排序与追踪。

**统计字段的结构归属**：RunMetricsSnapshot 是完整运行的汇总，TaskMetricsSnapshot（可按需增加）负责某个 task_id 的细粒度指标，LLMCallRecord/ToolCallRecord/ReviewEvent/CandidateEvent 属于可追踪的事实事件。所有统计数据由 Harness 的固定类创建并通过方法访问，不要求模型输出 JSON 或自行统计。

## 4. 模块详细设计与接口定义

本节 Python 函数签名是应实现的**接口声明和数据合同**；不是省略的实现代码。约定全局输入是权威数据，`task_id`、`candidate_version` 和 `run_id` 由 Harness 检查，所有读写返回类型必须可映射至第 3 章数据模型。

| `rlm_query_batched(task_ids: list[str]) -> list[TaskDispatchOutcome]` | 批量分发；每项独立记录结果/失败，便于局部补做 |

| `submit_root_answer(final_answer_ref: str | None, final_text: str |

**Root 模型可用 REPL 函数**统一包含 create_plan、add_task、set_task_acceptance、copy_plan、begin_plan_revision、commit_plan、get_plan_state、rlm_query、rlm_query_batched、list_accepted_results、read_accepted_result 与最终提交；不向模型暴露直接覆写 TaskLedger 的函数。因现有原型使用 `rlm_query(instruction, context)`，目标系统应统一升级为**任务 ID 驱动的 `rlm_query(task_id)`**，使派发天然受计划管控；若保留旧签名，只能作为内部兼容适配并在执行前登记 TaskSpec，禁止绕过 TaskLedger。

### 4.3 PlanManager / TaskLedger（全局计划与进度的权威组件）

**核心目标**：使 Root 在长任务执行中始终能获取全局目标、当前进度、已完成事项、未完成事项、已获得的有效结果、问题反馈和下一步可选行动，并能根据实际执行结果持续修订计划。**不预设使用 DAG、固定任务表、树、线性步骤列表或其他特定规划方法。**

**职责**：接收 Root 提出的计划或任务项；管理计划版本；保存已完成与待完成事项、验收状态、结果引用和问题；在 Root 请求时返回可用于下一轮规划的状态摘要；对计划调整和状态更新进行一致性校验。计划的内部存储可根据后续研究选择列表、图、分层计划、状态记录或组合结构。

**概念状态**：`plans`（全局计划历史）、`tasks`（可追踪的任务项）、`plan_version`、`accepted_results`、`open_issues`、`progress_summary`、`commit_keys`。它们是系统需要管理的语义信息，不意味着必须用某个指定的数据结构实现。

| 方法签名 | 行为及返回 |
| --- | --- |
| `create_plan_draft(run_id: str, goal: str, expected_version=None) -> str` | 创建受管理的计划草稿 |
| `copy_plan_draft(draft_id: str, goal=None) -> str` | 创建独立草稿副本 |
| `add_task_to_draft(draft_id: str, task: TaskDraft) -> None` | 增加可逐步补全的任务项 |
| `set_acceptance_on_draft(draft_id: str, task_id: str, acceptance: AcceptanceSpec, output: OutputSpec) -> None` | 设置验收条件 |
| `commit_plan_draft(draft_id: str) -> PlanReceipt` | 检查任务标识、输入与验收信息并登记计划，不强制验证 DAG |
| `get_task(run_id: str, task_id: str) -> TaskRecord` | 返回任务当前实际状态 |
| `get_plan_state(run_id: str) -> PlanState` | 返回目标、完成项、未完成项、异常反馈、结果引用和计划版本 |
| `list_pending_tasks(run_id: str) -> list[TaskRecord]` | 列出尚未完成的事项，不隐含任务依赖图 |
| `record_progress(run_id: str, task_id: str, status: str, evidence_ref: str | None) -> TaskRecord` |
| `transition_task(run_id: str, task_id: str, expected_status: str, new_status: str, event_id: str) -> TaskRecord` | 状态比较交换及幂等更新 |
| `revise_plan(run_id: str, expected_version: int, change: PlanChangeRecord) -> PlanReceipt` | 按版本记录计划修订原因、修改内容及其影响 |
| `validate_plan_completion(run_id: str) -> ValidationReport` | 根据全局用户目标、已接受结果、未完成事项与验收条件判断是否可结束 |
| `record_accepted_receipt(run_id: str, task_id: str, receipt: ResultReceipt, expected_task_version: int) -> TaskRecord` | 与 ResultStore 一致地记录被接受的结果 |

**任务组织规则**：当前只要求每个执行事项可追踪、可查询、可更新、可关联审核结果。是否存在任务依赖、执行顺序、任务树、优先级或允许并行，**均属于未来具体规划算法的可选能力**。因此，不能在核心接口中把“所有前驱 ACCEPTED”或“图必须无环”作为通用前提。如果后续选择依赖图策略，再在相应策略实现中增加专项校验。

**动态修订规则**：Root 能按最新反馈新增任务、修改尚未完成的任务、取消不必要任务、重新组织下一步动作或调整验收标准；Harness 保留版本与变更原因。已经 ACCEPTED 的事实结果不能被静默改写或重复计数；必要时应显式标记失效或创建新的核查项。全局目标不能因计划调整而被悄悄缩减。

**成功标准**：不论最终选用何种规划表示，Root 都能清楚知道整体任务目标、已完成什么、还缺什么、遇到什么障碍、哪些结果可信，以及是否达到最终完成条件。

### 4.4 SubAgentDispatcher（派发与子任务执行协调）

**职责**：消费 PlanManager 的任务合同，分配 ChildSession，提供安全的输入引用与预算，组织 Child 提交—Supervisor 审核—反馈循环，向 Root 只返回已接受 Receipt。
**核心变量**：`client`、`model`、`tools`、`agent_loop`、`child_sessions: dict[task_id,ChildSession]`、`records`、`max_subcalls`、`max_revisions`、`child_max_steps`、`supervisor_factory`。

| 方法签名 | 行为及返回 |
| --- | --- |
| `dispatch_registered(run_id: str, task_id: str) -> TaskDispatchOutcome` | 检查 TaskLedger、创建或恢复 Child、驱动候选审核 |
| `dispatch_batch(run_id: str, task_ids: list[str]) -> list[TaskDispatchOutcome]` | 逐任务执行并保留部分成功状态；首版允许顺序执行 |
| `create_child_session(run_id: str, task: TaskSpec) -> ChildSession` | 创建独立 REPL/messages/history 并挂接提交函数 |
| `run_until_submission(session: ChildSession) -> CandidateManifest | ChildOutcome` |
| `review_candidate(session: ChildSession, manifest: CandidateManifest) -> ReviewVerdict` | 创建/恢复 Supervisor 审核会话并等待裁决 |
| `resume_child(session: ChildSession, verdict: ReviewVerdict) -> CandidateManifest | ChildOutcome` |
| `get_child_session(run_id: str, task_id: str) -> ChildSession` | 内部获取会话（不能直接返回给 Supervisor REPL） |
| `get_task_execution(run_id: str, task_id: str) -> TaskDispatchOutcome` | 查询当前任务执行与提交状态 |

**失败逻辑**：模型异常、Child 达最大轮次、提交校验失败、审核拒绝至上限均须形成明确状态。`max_revisions` 与 `max_subcalls` 分开计费：同一 Child 的原地修复不算新派发，但应计入 LLM 调用和 Token 预算。不能将异常文本当作合法 ResultReceipt。

### 4.5 ChildAgent（独立子任务执行者）

**职责**：根据 TaskSpec 利用私有 REPL 访问数据、产生中间变量并显式提交候选。
**核心变量**：`run_id`、`task_id`、`task_version`、`messages`、`repl`、`history`、`submission_status`、`candidate_version`。Child 初始消息包含 task instruction / scope / acceptance / input_refs，而不包含 Root 的全部内部对话。

| 方法签名 | 行为及返回 |
| --- | --- |
| `start(task: TaskSpec, input_refs: list[str]) -> ChildSession` | 初始化 Child 专属模型上下文与 REPL |
| `run_until_submission(max_steps: int) -> ChildOutcome` | 循环推理/工具执行直到有效候选或失败 |
| `submit_candidate(result_var: str, evidence_vars: list[str] = [], summary: str = "") -> SubmissionAck` | 在 Child REPL 中提交变量名称；由 SubmissionRegistry 冻结 |
| `resume_after_feedback(verdict: ReviewVerdict, max_steps: int) -> ChildOutcome` | 对原 messages 追加审查反馈，使用原 REPL 继续生成 |
| `get_history(start: int = 0, limit: int = 100) -> list[StepRecord]` | 提供给 Harness 内部日志组件，不直接灌入 Supervisor 消息 |

**提交约束**：没有调用 `submit_candidate` 的纯文本 `stop` 只表示本次生成停止，**不等于结果已提交**。专用提交事件须由 REPLRuntime 与 SubmissionRegistry 联合确认，Child Agent Loop 在提交成功后返回 `SUBMITTED`，等待审核。若 Supervisor REVISE，继续使用原消息列表、原 REPL 和累计历史；新的候选版本在新执行边界生成。

### 4.6 REPLRuntime（Python 交互执行环境）

**职责**：为 Root、Child、Supervisor 维持互相独立的 REPL 命名空间；执行 Python，记录结构化执行状态，并支持与 Child 候选提交绑定的执行边界。

**核心变量**：`namespace: dict[str, object]`（Python 解释器运行时必需的命名空间，属于动态变量容器，**不是要求模型生成的业务 JSON 合同**）、`execution_id`、`agent_id`、`authorized_tools`、`submission_pending`。

| 方法签名 | 行为及返回 |
| --- | --- |
| `execute(code: str, \*, execution_id: str) -> ExecutionResult` | 返回执行成功与否、stdout/stderr、异常和提交事件的类型化对象 |
| `get_variable(name: str) -> object` | Harness 内部访问本 REPL 中对象 |
| `set_variable(name: str, value: object) -> None` | Harness 注入变量和受控函数 |
| `snapshot_variables() -> VariableCatalog` | 返回类型化变量目录及元数据，不默认加载大对象 |
| `get_execution_history(start: int, limit: int) -> list[ExecutionResult]` | 返回执行记录对象列表 |
| `freeze_variable(name: str, snapshot_id: str) -> ArtifactRef` | 冻结可支持的数据类型并产生不可变引用 |
| `register_submission_hook(callback: SubmissionCallback) -> None` | 将候选提交与代码单元成功结束绑定 |

**固定返回类**：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class SubmissionEvent:
    status: str
    result_var: str

@dataclass(frozen=True)
class ExecutionResult:
    execution_id: str
    success: bool
    stdout: str
    stderr: str
    error_type: str | None
    error_message: str | None
    submission_event: SubmissionEvent | None = None
```

执行代码后由 Harness 读取 `result.success`、`result.stdout`、`result.submission_event`；不让 Agent 手动输出以上 JSON。**提交时先记录意图，执行成功结束后再冻结变量**；若同一执行单元后续报错，不能将提交标记为成功。这里不能保证撤销任意 Python 外部副作用，因此仍需要受控运行环境。

REPL 的通用工具接口可保留 Python `dict` 命名空间，因为 Python `exec` 本身使用映射对象存储任意运行时变量；该命名空间不等于 Agent 间的数据协议。

### 4.7 SubmissionRegistry（候选提交与版本冻结）

**职责**：把 Child 在 REPL 中提出的结果变量转化为不可变、可被审核的 CandidateManifest；分配版本；保证一次代码执行的成功/失败与提交状态一致。
**核心变量**：`pending_submissions: dict[execution_id, SubmissionIntent]`、`manifests: dict[(run_id,task_id,version),CandidateManifest]`、`artifacts: ArtifactStore`、`candidate_counters`、`idempotency_keys`。

| 方法签名 | 行为及返回 |
| --- | --- |
| `prepare_submission(session: ChildSession, execution_id: str, result_var: str, evidence_vars: list[str], summary: str) -> SubmissionIntent` | 验证变量名存在且属于 Child，记录暂存提交意图 |
| `finalize_submission(session: ChildSession, execution: ExecutionResult) -> CandidateManifest` | 仅在代码单元成功时分配下一 candidate_version、冻结结果/证据、写 Registry |
| `abort_submission(execution_id: str, reason: str) -> None` | 若执行失败，撤销**提交意图**（不宣称回滚任意 Python 副作用） |
| `get_candidate(run_id: str, task_id: str, candidate_version: int) -> CandidateManifest` | 获取指定版本，不能自动降级到最新版 |
| `list_candidates(run_id: str, task_id: str) -> list[CandidateManifest]` | 查询版本历史 |
| `get_artifact(ref_id: str, *, offset: int = 0, limit: int = 1000, path: str | None = None) -> ArtifactView` |

**快照定义**：冻结的是提交时刻用于审核的结果和证据，不能给出 Child 原变量的裸地址。对 JSON 兼容值可以规范化序列化复制并计算哈希；对大文件采用不可变复制或内容寻址文件；其他对象必须有专用序列化器，否则拒绝提交。为了让 Supervisor 能枚举**全部中间变量**，冻结时生成完整的元数据目录；实际变量值按审核请求从稳定的冻结数据中读取。不能可靠冻结的变量在目录里标为 `UNAVAILABLE`，不得把其审查视作已完成。

### 4.8 StateBroker（跨 REPL 的只读审核访问）

**职责**：Supervisor 通过固定方法按需读取 Child 在提交时冻结的变量和执行证据，不能得到可修改的 Child REPL 对象。Broker 仅开放当前 `ReviewScope` 允许读取的 `(run_id, task_id, candidate_version)`。

**主要对象**：`ReviewScope`、`VariableInfo`、`VariableCatalog`、`ArtifactView`；均由 Harness 构造。列表与实际数据仅在 Supervisor 通过方法调用时读取，不需要模型生成复杂 JSON 查询协议。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class ReviewScope:
    run_id: str
    task_id: str
    candidate_version: int
    supervisor_id: str
    scope_id: str

@dataclass(frozen=True)
class VariableInfo:
    name: str
    type_name: str
    size_bytes: int
    available: bool
    snapshot_id: str
    evidence_ref: str | None

@dataclass(frozen=True)
class VariableCatalog:
    entries: tuple[VariableInfo, ...]
    snapshot_id: str

    def names(self) -> tuple[str, ...]:
        return tuple(getattr(item, "name") for item in self.entries)

@dataclass(frozen=True)
class ArtifactView:
    name: str
    path: str
    offset: int
    limit: int
    truncated: bool
    value: object
    evidence_ref: str
```

**接口约定**：

| 接口 | 作用 |
| --- | --- |
| `issue_review_scope(run_id: str, task_id: str, candidate_version: int, supervisor_id: str) -> ReviewScope` | 授予候选版本范围内的只读访问权 |
| `list_child_variables(scope: ReviewScope, include_all: bool = True) -> VariableCatalog` | 仅列出变量元数据，不自动传入全部值 |
| `inspect_child_variable(scope: ReviewScope, name: str, path: str | None = None, offset: int = 0, limit: int = 1000) -> ArtifactView` |
| `read_candidate(scope: ReviewScope) -> CandidateManifest` | 查看候选元数据和结果引用 |
| `get_child_trace(scope: ReviewScope, start: int = 0, limit: int = 50) -> list[TraceRecord]` | 读取分页执行记录 |
| `get_task_contract(scope: ReviewScope) -> TaskSpec` | 查询子任务合同 |
| `get_global_task(scope: ReviewScope, include_full: bool = False) -> GlobalTaskSpec` | 查询权威全局目标 |
| `get_plan_context(scope: ReviewScope) -> PlanContextView` | 查询整体进度及相关已完成工作 |
| `read_artifact(scope: ReviewScope, ref_id: str, offset: int = 0, limit: int = 1000, path: str | None = None) -> ArtifactView` |
| `revoke_review_scope(scope: ReviewScope) -> None` | 审核结束后回收权限 |

**Supervisor REPL 的直接调用示例**（由 SupervisorSession 绑定当前 scope，无需模型显式拼装 ReviewScope）：

```python
catalog = list_child_variables()
print(catalog.names())
view = inspect_child_variable("analysis", path="\$.ratio")
print(view.value)
print(view.evidence_ref)
```

`ArtifactView.value` 允许是原始数据的不可变副本、基本 Python 值或经过受控处理的动态结构；**它本身属于任务未知数据，不适合强制用一套固定业务类描述**。同一任务不同 Candidate 的变量必须严格按提交版本隔离，Supervisor 的读取不得修改 Child 的真实 REPL。超限返回应设置 `truncated=True`，不得让截断结果被误判为完整证据。

### 4.9 SupervisorAgent（带独立 REPL 的审核者）

**职责**：在持有独立模型上下文和独立 Python REPL 的前提下，理解全局目标/子任务验收条件，主动探查 Candidate 和 Child 中间变量，复验计算与逻辑，提交结构化审核裁决。
**核心变量**：`review_id`、`review_scope`、`task_id`、`candidate_version`、`messages: list[Message]`、`repl: REPLRuntime`、`history: list[StepRecord]`、`max_review_steps`、`review_budget`、`verdict: ReviewVerdict | None`。

Supervisor 启动时的最小模型上下文包含：GlobalTaskSpec 的目标与约束摘要、受审 TaskSpec 的任务目标与验收条件、CandidateManifest 的提交引用与版本、PlanContextView 的当前整体进度和相关已完成结果，以及审核工具说明。完整原始输入、Child 消息和全部中间变量不默认注入模型上下文。

| 方法签名 | 行为及返回 |
| --- | --- |
| `start_review(run_id: str, task_id: str, candidate_version: int) -> ReviewSession` | 获取 ReviewScope，创建独立 REPL/messages/history |
| `run_review_loop(session: ReviewSession, max_steps: int) -> ReviewOutcome` | 模型自主决定调用读取工具或在独立 REPL 计算，直到显式提交 Verdict |
| `list_child_variables(include_all: bool = True) -> VariableCatalog` | Supervisor REPL 中的只读变量目录接口，返回固定类实例 |
| `inspect_child_variable(name: str, path: str | None = None, offset: int = 0, limit: int = 1000) -> ArtifactView` |
| `read_candidate() -> CandidateManifest` | 获取待审核变量句柄 |
| `get_child_trace(start: int = 0, limit: int = 50) -> list[TraceRecord]` | 读取受审任务的工具轨迹 |
| `get_global_task(include_full: bool = False) -> GlobalTaskSpec` | 按需核查原用户要求 |
| `get_task_contract() -> TaskSpec` | 获取子任务验收标准 |
| `get_plan_context() -> PlanContextView` | 获取整体目标、已完成与未完成任务以及相关背景 |
| `submit_review(task_id: str, candidate_version: int, decision: str, finding: str, evidence_refs: list[str], requested_action: str = "") -> ReviewSubmissionAck` | 在其 REPL 中显式提交结构化审核决定 |
| `close_review(session: ReviewSession, outcome: ReviewOutcome) -> None` | 写入审核轨迹并撤销读取权限 |

**审核终止条件**：只有成功调用 `submit_review` 并被 Harness 确认，才产生有效 Verdict。Supervisor 的普通文字 `stop` 不视为有效审查。最大审核轮次、模型超时、工具读取失败等情况统一转成 `REVIEW_INCOMPLETE`，严禁自动 ACCEPT。

**审核原则**：Supervisor 可以自行决定需要查看哪些变量；必须优先按目标和验收条件核查，而不是阅读全部变量。判断应区分格式、覆盖度、可复算性及任务目标一致性；证据缺失时须保留不确定性。若原因是子任务本身不可能完成或规划范围冲突，返回 `PLAN_ISSUE` 由 Root 处理。

### 4.10 ReviewGate / ResultStore（审核门控和提交）

**职责**：验证 Verdict 的来源、结构、候选版本和证据引用；唯一的正式 ACCEPT/Commit 权威，避免未经审查的结果污染全局计划。
**核心变量**：`verdicts: dict[review_id,ReviewVerdict]`、`accepted: dict[(run_id,task_id),ResultReceipt]`、`commit_keys`、`result_refs`。

| 方法签名 | 行为及返回 |
| --- | --- |
| `validate_verdict(scope: ReviewScope, verdict: ReviewVerdict) -> ValidationReport` | 检查枚举、必填字段、scope/task/version 对齐、证据引用合法性及版本 |
| `apply_verdict(scope: ReviewScope, verdict: ReviewVerdict) -> ReviewApplyOutcome` | 按决策转移任务状态；拒绝不合法格式 |
| `commit_accepted_candidate(run_id: str, task_id: str, candidate_version: int, review_id: str, expected_task_version: int) -> ResultReceipt` | 幂等、原子地写 ResultStore + TaskLedger 已接受状态 |
| `get_receipt(run_id: str, task_id: str) -> ResultReceipt | None` |
| `list_accepted_results(run_id: str) -> list[ResultReceipt]` | Root 查询全局有效结果 |
| `read_accepted_result(receipt_id: str, path: str | None = None, offset: int = 0, limit: int = 1000) -> ArtifactView` |

**门控不变量**：`ACCEPT` 是 Supervisor 判断，`COMMITTED/ACCEPTED` 是 Harness 完成状态更新之后的结果；两者必须分开记录。事务重复调用必须返回同一 Receipt，不得重复累计；旧 `candidate_version` 的迟到 Verdict 不可覆盖新版本。

### 4.11 统一接口错误合同（固定类）

Agent 和 Harness 之间的受控调用使用 `ToolResponse[T]` 对象描述结果和失败原因，不要求模型自行生成错误 JSON。尤其要区分“工具执行失败”“审核未完成”“Child 提交被拒绝”。

```python
from dataclasses import dataclass
from enum import StrEnum
from typing import Generic, TypeVar

T = TypeVar("T")

class ErrorCode(StrEnum):
    INVALID_ARGUMENT = "INVALID_ARGUMENT"
    PLAN_INVALID = "PLAN_INVALID"
    TASK_NOT_DISPATCHABLE = "TASK_NOT_DISPATCHABLE"
    TASK_NOT_FOUND = "TASK_NOT_FOUND"
    VERSION_CONFLICT = "VERSION_CONFLICT"
    SUBMISSION_MISSING = "SUBMISSION_MISSING"
    UNSUPPORTED_ARTIFACT = "UNSUPPORTED_ARTIFACT"
    ARTIFACT_TOO_LARGE = "ARTIFACT_TOO_LARGE"
    REVIEW_INCOMPLETE = "REVIEW_INCOMPLETE"
    PERMISSION_DENIED = "PERMISSION_DENIED"
    BUDGET_EXCEEDED = "BUDGET_EXCEEDED"
    MODEL_REQUEST_FAILED = "MODEL_REQUEST_FAILED"
    EXECUTION_FAILED = "EXECUTION_FAILED"
    ALREADY_ACCEPTED = "ALREADY_ACCEPTED"

@dataclass(frozen=True)
class ToolResponse(Generic[T]):
    ok: bool
    data: T | None = None
    code: ErrorCode | None = None
    message: str = ""
    retryable: bool = False

    @classmethod
    def success(cls, data: T) -> "ToolResponse[T]":
        return cls(ok=True, data=data)

    @classmethod
    def failure(
        cls, code: ErrorCode, message: str, retryable: bool = False
    ) -> "ToolResponse[T]":
        return cls(
            ok=False,
            code=code,
            message=message,
            retryable=retryable
        )
```

**内部处理示例**：

```python
result = ToolResponse.failure(
    ErrorCode.VERSION_CONFLICT,
    "Plan version changed",
    retryable=True
)
print(result.ok)
print(result.code)
```

工具层负责将异常转换为受控响应；Root/Child/Supervisor 通过 `ok`、`code` 和 `data` 分支处理。注意模型仍通过 Chat Completions 的 `messages/tool_calls` 协议接收**经过限制大小的工具观察文本**；Python 类不意味着可以把任意对象完整传进模型上下文。Harness 负责必要的受控格式化或序列化，禁止用异常字符串猜测错误类型。

### 4.12 MetricsCollector / RunRecorder（运行统计与追踪）

**职责**：作为现有 Agent Loop、全局规划与 Supervisor 审核链路的共用观测组件，接收真实执行事件，输出按 Run/Task/Agent Role 汇总的指标。它**不参与任务决策，不是新的 Agent，不控制计划表示，也不修改审核结果**。

**持有状态**：`run_clocks`、`llm_events`、`tool_events`、`candidate_events`、`review_events`、`task_status_events`、`event_ids_seen`。底层事件以 `event_id` 去重，可按 `run_id`、`task_id`、`agent_role`、`candidate_version` 查询。可先保存在内存中，结束时由 Harness 写入文件；不会把完整日志默认塞进模型上下文。

**固定接口签名：**

```python
class MetricsCollector:
    def start_run(self, run_id: str) -> None: ...
    def finish_run(self, run_id: str, status: str) -> RunMetricsSnapshot: ...

    def record_llm_call(self, event: LLMCallRecord) -> None: ...
    def record_tool_call(self, event: ToolCallRecord) -> None: ...
    def record_candidate(self, event: CandidateEvent) -> None: ...
    def record_review(self, event: ReviewEvent) -> None: ...
    def record_task_state(self, event: TaskStateEvent) -> None: ...

    def get_run_metrics(self, run_id: str) -> RunMetricsSnapshot: ...
    def get_task_metrics(self, run_id: str, task_id: str) -> TaskMetricsSnapshot: ...
    def get_role_metrics(self, run_id: str, role: AgentRole) -> RoleMetricsSnapshot: ...
    def export_run(self, run_id: str, output_path: str) -> str: ...
```

`TaskStateEvent`、`TaskMetricsSnapshot` 和 `RoleMetricsSnapshot` 采用与第 3.9 节一致的固定 `dataclass` 约定；它们是后续可扩展的角色/任务统计视图，不要求 Root 输出复杂字典。

**采集位置与执行顺序：**

1. `SessionRuntime.start_run()` 调用 `metrics.start_run(run_id)`；记录实际起始单调时钟值。
2. `call_llm()` 的每次模型请求在 `finally` 路径生成 `LLMCallRecord`，包含 AgentRole、模型 ID、耗时、成功状态、finish_reason、Token usage；失败也必须记时。
3. `agent_loop()` 负责关联 `run_id/task_id/agent_role`，工具请求进入 `do_repl()` 后由工具分发器登记一次 `ToolCallRecord`；代码格式、参数校验、用户拒绝、执行失败均独立标注。
4. `SubmissionRegistry.finalize_submission()` 在 Candidate 真正冻结成功后发送 `CandidateEvent(SUBMITTED)`；被拒绝或取消的提交意图不算有效提交。
5. `ReviewGate.apply_verdict()` 对通过校验的审核结果生成一次 `ReviewEvent`，由 `event_id` 与 `review_id` 保证不重复计数；REVISE、PLAN_ISSUE、REVIEW_INCOMPLETE 分类统计。
6. `SubAgentDispatcher.resume_child()` 在真正开始执行修复时累积修复尝试，不能在 Supervisor 刚输出 REVISE 时提前记为已执行。
7. `TaskLedger` 更新任务状态时记录 `TaskStateEvent`；已接受任务数从权威账本派生，不能靠重复累计模型返回值。
8. `SessionRuntime.finalize_run()` 或 `abort_run()` 必须调用 `metrics.finish_run()`；外层异常和提前退出应由 `finally` 补写结束事件，并标记非成功状态。生成固定类 `RunMetricsSnapshot`，附带到 `RunOutcome` 的 `metrics_ref` 或通过 `get_run_metrics(run_id)` 查询。
9. 完整事件日志可写入结构化文件以支持科研复盘；日志里含潜在敏感代码、输入和输出，应与公共仓库隔离，日志文件不能自动提交 Git。

**实现上的关键要求**：

- **尽量在 Harness 的确定性边界采集**，不让 Agent 在 Prompt 中自报执行次数、耗时和准确率。
- `time.perf_counter_ns()` 只用于计算历时；`datetime.now(timezone.utc)` 可用于事件时间戳。不同主机/进程的 perf_counter 值不应跨进程直接相减；跨进程需要各自记录阶段时长并由协调器测量端到端时间。
- Token usage 缺失时保留 `None`，或者记录明确来源的估算值；不可无标注混合实测与估算。输入/输出 token 应按 Root、Child、Supervisor 分别统计，避免只报告总数而看不出审核成本。
- Tool 执行成功要根据 `ExecutionResult.success`，未知工具、JSON 参数损坏、用户拒绝、Python 运行异常分别编码；若无法判定语义正确性，`semantic_correct=None`。
- 重复事件必须去重；模型请求自动重试应当分别统计尝试次数与最终请求数，具体约定由统一的 LLM Client 落地。
- 对 `REVISE` 后的 Child 原地修复，必须保留候选版本、审核 ID、修复尝试与后续结果的因果关联，便于计算修复是否真正使任务被 ACCEPT。
- **指标输出不进入默认 Agent Prompt**：Root 如需成本/进度可调用 `get_run_metrics()` 获取摘要，原始事件需要单独明确查询。

### 4.13 统计对现有模块的接口影响

| 既有模块 | 需要增加的采集点 | 核心数据 |
| --- | --- | --- |
| SessionRuntime | start_run / finalize_run / abort_run | 全局墙钟耗时、运行状态、最终统计引用 |
| Root / Child / Supervisor Agent Loop | 每次 LLM 请求及其角色上下文 | 请求次数、Token、模型延迟、模型结束原因 |
| ToolRegistry / do_repl / REPLRuntime | 每条 tool call 请求与执行结束 | 协议合规、参数有效、执行成功、执行时长 |
| SubmissionRegistry | 成功冻结候选 | 提交次数、任务 ID、候选版本 |
| ReviewGate | 有效审核裁决和正式提交 | ACCEPT / REVISE / PLAN_ISSUE / REVIEW_INCOMPLETE 次数 |
| Dispatcher | 每次真正发生的原地继续 | 修复次数、候选序列、最终接受情况 |
| TaskLedger | 状态成功变更 | 完成任务数、失败任务数和进度 |
| MetricsCollector | 聚合、查询、导出 | RunMetricsSnapshot 及事件清单 |

**保持结构克制**：只有 MetricsCollector 是必要的公共统计组件，不引入独立监控 Agent、复杂消息总线或长期经验系统。最初可由同步函数调用上报事件，之后如有性能瓶颈再调整采集方式。

## 5. 状态机与控制规则

### 5.1 任务执行与审核状态转换

任务内部需要可追踪的执行状态，但**计划本身采用什么表示、如何选择任务、任务之间有无依赖，均不在此规定**。下面的状态机只约束“一个任务从开始执行到接受结果”的过程，不要求 DAG 或前置任务检查。

```
PLANNED --(Root 选择执行且 Harness 校验)--> RUNNING
RUNNING --(候选冻结成功)---------------> SUBMITTED
SUBMITTED ----------------------------> REVIEWING
REVIEWING --(ACCEPT + 正式提交)--------> ACCEPTED
REVIEWING --(REVISE)-------------------> REPAIRING
REPAIRING --(同一 Child 继续)----------> RUNNING
REVIEWING --(PLAN_ISSUE)---------------> PLAN_ISSUE
REVIEWING --(证据不足或审核错误)--------> REVIEW_INCOMPLETE
RUNNING/REPAIRING --(严重错误或预算耗尽)-> FAILED
PLANNED --(合法计划修改)---------------> CANCELLED
```

这里的 `PLANNED` 仅表示“已记录但尚未执行”，不要求一个任务必须排队等待其他任务；如何产生下一次执行动作由 Root 和未来选定的规划策略负责。不能从 `RUNNING` 直接跳到 `ACCEPTED`，也不能把 `REVIEW_INCOMPLETE` 当作通过审核。被接受的结果不能通过重复状态转移再次计数。

### 5.2 规划与审核之间的反馈关系

- `REVISE` 只说明当前任务的一个候选失败；不表示整个 Root 计划错误。反馈应具体到证据、错误性质和下一步修复动作，追加到同一 ChildSession，不能丢弃此前有效变量。
- PLAN_ISSUE 指审核发现任务目标、数据范围、验收条件或整体计划安排存在问题，例如必要输入缺失、任务覆盖不完整、子任务与全局目标不一致。Supervisor 返回诊断，由 Root 调整计划；不预设问题只能由依赖图冲突引起。
- `REVIEW_INCOMPLETE` 指审查本身缺证据/预算/格式失败，不应假定 Child 错误；Root 可安排补证据、补审核或停止。
- 全局计划进度以 `TaskLedger` 为权威；Root 的自然语言笔记不是状态数据库。

### 5.3 计划修订与可追溯性

计划修订需要版本约束，避免 Root 使用过时进度覆盖新状态。每次修订记录修改前后版本、涉及的任务或计划部分、修改原因、受影响的未完成事项和校验结果；具体的计划结构及相互关系由后续方案决定。

更新计划不得自动修改已接受 ResultReceipt；如果新计划使旧证据不适用，需产生显式 `SUPERSEDED` 关系及重验任务，并在最终完成检查中排除失效结果，禁止重复计数。这属于全局计划正确性所必需的版本规则，而非额外的独立功能。

### 5.4 审核会话连续性和预算

同一逻辑 Child 的每次 `candidate_version` 都指向同一 `ChildSession` 的连续执行；每次提交冻结不同版本。Supervisor 也可以为同一 task 保留独立审核对话以知道此前拒绝的原因，但每次必须明确当前 candidate_version，并重新绑定 ReviewScope。已失效版本不能获得写入权限。`max_revisions`、`max_review_steps`、`max_child_steps` 和全局模型 Token/调用预算必须同时生效，避免审核与修复无限循环。

## 6. 关键安全与一致性设计决策

**固定结构的统一处理原则**：PlanSpec、TaskSpec、AcceptanceSpec、OutputSpec、GlobalTaskSpec、TaskRecord、ArtifactRef、CandidateManifest、SubmissionAck、ReviewVerdict、ResultReceipt、ExecutionResult、ReviewScope、VariableCatalog、ArtifactView、ToolResponse 等固定协议数据全部使用 Harness 内部类型化类；Root、Child、Supervisor 通过类暴露的受控函数或 REPL 中注入的绑定方法操作，不负责生成完整 JSON。对计划采用可编辑 PlanDraft/TaskDraft 与正式不可变 PlanSpec/TaskSpec 两阶段转换；需要复制计划时使用 copy_plan 生成独立草稿。只有在存储和跨进程边界才由 Harness 控制 JSON 序列化与反序列化。受控函数能降低格式失配，但无法消除模型生成无效参数、无效代码或语义规划错误，因此仍须进行类型、值域、权限与业务逻辑验证。

| 设计议题 | 决策 | 理由与边界 |
| --- | --- | --- |
| Supervisor 能否访问 Child REPL | **可以读取提交时的受控冻结视图；不得直接得到可变 child_repl** | 避免审核修改证据；可按需查看全部变量目录及指定变量值 |
| Supervisor 是否有 REPL | **有，且独立** | 可主动计算、交叉检查和记录自己的中间变量 |
| Child 如何提交答案 | `submit_candidate(result_var, evidence_vars, summary)` | 大对象留在 REPL/ArtifactStore，跨代理只传引用 |
| Supervisor 初始上下文 | 全局任务合同摘要 + 子任务合同 + 候选 Manifest + 可用工具 + 计划依赖背景 | 审核有目标，但不强占模型上下文 |
| 何时正式更新全局进度 | `ACCEPT` 通过 ReviewGate 原子提交后 | 禁止候选答案直接污染全局状态 |
| 修复是否重建 Child | 不重建，使用原 REPL、messages、history | 保留此前有效计算结果、避免无意义重算 |
| 发现计划问题由谁修改 | Root 提出，PlanManager 校验 | 明确权责，避免 Reviewer 越权 |
| 如何处理任意 Python 对象 | 支持的格式冻结；不支持则拒绝或提供专用序列化器 | 普通 deepcopy 不是所有对象的安全快照 |
| 如何处理底层 exec 副作用 | 受限进程/容器隔离 + 只在受管 ResultStore 进行正式提交 | Python exec 字典隔离不等于 OS 隔离或全局回滚 |

**不可混淆的两个概念**：

1. **变量可见性**不等于**变量值全部进入模型上下文**：Broker 可以列出几千个变量元数据，Supervisor 只取其中必要的值/片段。
2. **冻结提交版本**不等于**能完全回滚 Python 执行环境**：结果门控保障受管理的全局结果一致性；任意文件操作、网络操作和不可序列化对象需要单独权限与执行隔离。

## 7. 系统验收要求与测试用例

### 7.1 Root 全局规划与进度维护

| 测试 | 输入/条件 | 预期 |
| --- | --- | --- |
| 计划创建 | Root 用 create_plan/add_task/commit_plan 登记整体目标与两个任务 | 成功记录目标、任务与版本，不要求预设 DAG |
| 进度可见 | 一项完成、一项未完成 | get_plan_state 准确返回已完成项、未完成项及已接受结果引用 |
| 长任务连续性 | Root 多轮分发、审核、修复后继续规划 | 不丢失当前目标、既有任务记录及完成进度 |
| 反馈驱动修订 | Supervisor 返回 PLAN_ISSUE | Root 可以基于反馈更改任务内容或新增行动，修改记录可追溯 |
| 重复任务标识 | 两项使用同一 task_id | 拒绝歧义或重复登记 |
| 版本冲突 | 用过期 expected_version 提交修订 | 返回 VERSION_CONFLICT，保留有效计划 |
| 不完整任务 | 仍存在必要任务或用户目标未覆盖 | finalize_run 不得声称成功 |
| 重复结果事件 | 同一已接受结果重复送达 | 全局完成计数不重复 |
| 规划策略可替换 | 更换计划内部结构或任务选择策略 | Root 仍能查询目标、进度、问题与结果，不依赖 DAG API |

### 7.2 Child 提交与 Supervisor 核查

| 测试 | 输入/条件 | 预期 |
| --- | --- | --- |
| 变量引用提交 | Child 有 analysis 变量，调用 submit_candidate | 得到 Manifest/ArtifactRef，不复制全文到 Root |
| 变量不存在 | result_var 不在 Child namespace | SUBMISSION_MISSING |
| 执行失败 | 提交意图产生后同一代码单元报错 | 不产生有效 SUBMITTED |
| 候选不可变 | 提交 v1 后 Child 修改原变量 | Supervisor 读 v1 仍得到冻结值 |
| 完整变量目录 | Child 有 result、cache、raw_data | 可枚举全部元数据；按需分别读取 |
| Supervisor 只读 | Reviewer 尝试改写 Child 变量 | 拒绝，Child 状态不变 |
| 独立计算 | Supervisor 在自己的 REPL 复算 | 只改变自己的变量 |
| 原地修复 | v1 REVISE，v2 ACCEPT | 同一个 Child REPL/messages/history；只提交 v2 |
| 旧判决迟到 | v1 判决误用于 v2 | VERSION_CONFLICT，不提交 |
| 审核缺证据 | 模型没有有效 evidence_ref | REVIEW_INCOMPLETE，不能 ACCEPT |
| 计划问题 | 子任务要求与用户目标冲突 | PLAN_ISSUE 通知 Root，不自动更改计划 |
| 幂等提交 | 重复写入相同 ACCEPT/Receipt | 只产生一份有效结果 |
| 过大变量 | 按需分页读取超出上限 | 返回 truncated/next_offset；不默认为完整 |
| 预算终止 | 修复/审核次数超限 | 明确失败或不完整状态，无无限循环 |

### 7.3 端到端验收路径

用一个可人工复算的两组统计任务运行：Root 登记两项 TaskSpec；Child A 提交 v1 并被 Supervisor REVISE；Child A 保留原变量修复并提交 v2，被 ACCEPT；Child B 被 ACCEPT；TaskLedger 的两个 required 任务都转 ACCEPTED；Root 读取两个 Receipt 并汇总；最终完成门控通过。这条测试同时确认模型消息上下文不会自动包含 Child 的整个变量空间，并检查没有重复计数。

### 7.4 运行统计验收与科研对照测试

统计验证应使用可控的 Fake Agent Loop / Fake Supervisor / Fake Tool，先验证事实计数和时间边界，再接入真实模型测试。

| 测试条件 | 预期统计结果 |
| --- | --- |
| 一次 Run 调用 Root 1 次、Child 2 次、Supervisor 2 次 LLM | `llm_calls=5`，并能按 AgentRole 拆分 |
| 某次模型 API 请求超时 | 请求数增加、失败数增加、记录耗时，最终 Token usage 可为 None |
| 工具调用缺失 ID、参数格式损坏、执行无异常、执行抛错各一次 | `tool_calls=4`；协议合法率、参数有效率、执行成功率分别计算，互不混用 |
| 只有 stdout，没有独立标准答案 | 可统计执行成功，但 `semantic_correct=None`；Tool Call 语义准确率显示 N/A |
| 一次审核 REVISE、原地继续一次、再次审核 ACCEPT | `candidates_submitted=2`、`candidates_rejected=1`、`candidates_accepted=1`、`repair_attempts=1`、`repaired_tasks_accepted=1` |
| 审核结果是 PLAN_ISSUE | 不计入 REVISE 次数，应单列 `plan_issues=1` |
| 审核超时/证据不足 | 记一次 REVIEW_INCOMPLETE，不计为 ACCEPT 或 REVISE |
| 同一 review_id 重复处理 | 事件只统计一次，任务完成计数不增加第二次 |
| 并发两个 Child，各执行约 1 s | Run 实际耗时约取决于并发墙钟，不强行等于两个 Child 时长之和 |
| Root 整体任务失败或用户中止 | 依然生成非成功状态及截至终止时的耗时、计数与可用 Token 数据 |
| 提交意图产生后当前 REPL 代码抛错 | 有效提交数不增加，提交失败单列 |
| 模型未返回 usage | Token 字段不填 0 冒充实测，覆盖率和来源正确 |
| 不同候选版本的 REVISE/ACCEPT | 审核结果严格绑定 task_id 和 candidate_version，修复记录不跨任务串号 |

**必要科研对照**：原始 RLM（无审核）与监督式 RLM 至少用同一任务、模型与预算条件报告：最终正确率或 F1、整次任务耗时、模型调用次数、Root/Child/Supervisor 的输入输出 Token、Tool Call 合规/成功率、候选提交与 REVISE 次数、修复成功率。带独立标准答案的实验可额外计算 Tool Call 语义准确率与 Supervisor 误接受/误拒绝；无真值时不能声称这些准确率已被测量。

## 8. 代码组织与依赖方向

目标模块划分：

```
supervised_rlm/
  client.py              # OpenAI SDK 模型调用、通用 agent_loop 与入口适配
  repl.py                # 通用 REPLRuntime
  runtime.py             # SessionRuntime / RunHandle
  root_agent.py          # RootAgent 规划与收尾控制
  plan_manager.py        # PlanManager + TaskLedger
  subagent.py            # SubAgentDispatcher + ChildSession
  submission.py          # SubmissionRegistry / CandidateManifest
  state_broker.py        # Supervisor 的只读证据访问 API
  supervisor.py          # SupervisorAgent + 审核 Agent Loop
  review_gate.py         # ReviewGate / ResultStore
  schemas.py             # 类型、状态枚举、数据合同、错误码
  metrics.py             # MetricsCollector + 类型化运行事件/指标汇总
tests/
  test_plan_validation.py
  test_plan_progress.py
  test_submissions.py
  test_review_broker.py
  test_supervisor_repair.py
  test_result_commit.py
  test_end_to_end.py
  test_metrics.py         # 耗时、Token、Tool Call、REVISE/修复计数口径验收
```

**依赖方向**：`schemas` 被所有模块引用；`runtime` 组装组件；`root_agent` 调用 `plan_manager` 和 `subagent` 暴露的受控接口；`subagent` 驱动 `child_agent_loop`、`submission`、`supervisor` 和 `review_gate`；`supervisor` 只能通过 `state_broker` 读受审证据；`review_gate` 负责将通过审核的结果写入 `plan_manager` 的任务状态和受管结果存储。不得让 `supervisor.py` 直接 import Root 的全局变量字典并任意修改。
